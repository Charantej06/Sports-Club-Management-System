1. Executive Architecture & Invariant Rules

Champions Club is built as a modular Next.js App Router monolith following Domain-Driven Design (DDD) and Clean Architecture principles. It solves real-world athletic club operations across court reservations, membership subscriptions, retail e-commerce/POS, restaurant dining, staff HR/payroll, and financial double-entry accounting.

Core Engineering Invariants (Examiner Must-Knows)

  • Server-Authoritative Pricing: Clients never submit prices, discounts, or roles. The server queries the database, applies plan snapshots, and enforces the source of truth.
  • Integer Paise Representation: All monetary values are 64-bit integers in Indian Paise (₹1.00 = 100 paise). Eliminates IEEE-754 floating-point rounding errors (e.g. 0.1 + 0.2 !== 0.3).
  • Asia/Kolkata Business Calendar: All timestamps persist in UTC (ISO 8601), but operational club days (06:00 to 23:00), daily quotas, and court schedules evaluate strictly in Asia/Kolkata timezone.
  • Immutable Financial Snapshots: Once an invoice is issued, database triggers prevent mutations to line items or totals. Plan benefits and pricing snapshots are frozen in JSON columns at purchase time.
  • High-Concurrency Protection: Simultaneous race conditions (booking the same court, buying the last racket in stock, claiming the final mixer slot) are defeated at the database engine level using PostgreSQL GiST exclusion constraints and row-level locks (SELECT FOR UPDATE).
System Structure Mapping src/app/api/*: Authenticates cookies via Better Auth, validates input via strict Zod schemas.
src/modules/*: Isolated business domains (bookings, shop, clubhouse, billing, membership, operations).
src/worker.ts: Independent Node daemon claiming outbox jobs via FOR UPDATE SKIP LOCKED.

2. Prisma ORM & Schema Deep-Dive

What is Prisma ORM? Prisma is a modern, next-generation TypeScript Object-Relational Mapper (ORM) composed of:

  1. Prisma Schema (schema.prisma): The declarative single source of truth describing models, relations, enums, data types, and database mappings.
  2. Prisma Client (@prisma/client): An auto-generated, type-safe query builder that compiles TypeScript method calls (e.g. tx.reservation.create()) into optimized SQL queries.
  3. Prisma Migrate: Declarative migration engine tracking database schema evolution via versioned SQL migration folders in prisma/migrations.
  4. Prisma Query Engine: A high-performance binary/Rust-backed query engine that manages connection pools, prepares parameterized SQL statements (preventing SQL injection), and maps relational rows to structured JSON objects.

2.3 The "Little Things" in Schema That Examiners Grill On

Prisma AttributeWhat it Means Under the HoodWhy It Was Chosen / Examiner Gotcha
@id Defines the Primary Key constraint (PRIMARY KEY in SQL). Every database entity requires a unique identifier.
@default(cuid()) Generates a Collision-resistant Unique Identifier (CUID) on insert. Unlike integer auto-increments (1, 2, 3), CUIDs are unpredictable (prevents enumeration attacks) and safe in distributed environments without central coordination.
@unique Creates a SQL UNIQUE constraint on a single column. e.g. email or championsId. Database rejects duplicate inserts instantly with error code P2002.
@@unique([colA, colB]) Composite Unique Constraint spanning two or more columns. e.g. @@unique([department, originId]) prevents an origin order/booking from generating multiple invoices! Or @@unique([userId, key]) in Checkout for idempotency.
@@index([colA, colB]) Composite B-Tree Index in PostgreSQL. Crucial for performance! e.g. @@index([courtId, startsAt]) allows PostgreSQL to instantly look up court slots in O(log N) instead of scanning the entire table (O(N)).
@db.Timestamptz(3) PostgreSQL TIMESTAMP WITH TIME ZONE with 3-digit microsecond precision. Stores explicit UTC offsets. Prevents daylight saving or server clock skew bugs across date calculations.
@db.Date PostgreSQL DATE type (year-month-day only, without time). Used for clubDay and dateOfBirth. Prevents timezone shifts from changing a user's birthday or club date.
Json PostgreSQL JSONB binary JSON storage. Used for planSnapshot and priceSnapshot. Stores immutable historical snapshots of benefits and discounts at the exact second of purchase.
@relation(..., onDelete: Cascade) Foreign key cascade deletion constraint. When a parent User is deleted, its associated Session and Account rows are automatically deleted by the database engine.

3. Concurrency Protection & SQL Migrations

A common examiner question is: "Why can't Prisma do everything? Why did you write custom SQL migrations?"
The Answer: Prisma ORM excels at standard relational mappings and CRUD, but cannot express advanced PostgreSQL engine-level primitives like GiST Exclusion Constraints, Transactional Advisory Locks, and Row-level Snapshot Triggers. These live in the versioned SQL migrations!

3.1 The GiST Exclusion Constraint (Zero Overlap Invariant)

In prisma/migrations/202610030001_foundation/migration.sql:

CREATE EXTENSION IF NOT EXISTS btree_gist;

ALTER TABLE "Reservation" 
ADD CONSTRAINT "court_no_overlap" 
EXCLUDE USING gist (
  "courtId" WITH =, 
  tstzrange("startsAt", "endsAt", '[)') WITH &&
) WHERE (status IN ('HOLD', 'CONFIRMED'));
How This Defeats Concurrency Races (Examiner Viva Answer) If two players click the exact same court and hour slot at the exact same millisecond:
  1. Both requests arrive at different Node.js worker threads.
  2. Both threads attempt to insert a Reservation with status HOLD.
  3. The PostgreSQL storage engine evaluates the GiST index. It detects that the two time intervals [startsAt, endsAt) overlap (&&) for the identical courtId (=).
  4. PostgreSQL allows transaction #1 to commit and instantly aborts transaction #2 with SQL error code 23P01 (Exclusion Violation). Double-booking is mathematically impossible!

3.2 Deterministic Row-Level Locking (Deadlock Prevention)

When purchasing multiple inventory items or settling bills, how do we lock rows without deadlocking? Look at src/modules/shop/service.ts:

async function stockLock(tx: Tx, ids: string[]) {
  // Sort variant IDs deterministically to prevent cyclic lock waits (deadlocks)!
  for (const id of [...new Set(ids)].sort())
    await tx.$queryRaw`SELECT id FROM "ProductVariant" WHERE id=${id} FOR UPDATE`;
}
Why Sorting by ID Matters (Deadlock Explanation) Suppose User A buys Item 1 and Item 2, while User B buys Item 2 and Item 1 simultaneously.
Without sorting: User A locks 1 and waits for 2; User B locks 2 and waits for 1. Deadlock!
With .sort(): Both transactions must acquire lock on Item 1 first, then Item 2. One transaction waits cleanly without crashing!

3.3 PostgreSQL Advisory Locks

In guard_daily_quota() (migration 202610030002_operations):

PERFORM pg_advisory_xact_lock(hashtextextended(member_id, 0));

Locks the member's daily quota counter across concurrent transactions. If a member opens 3 tabs to book 3 courts simultaneously to exceed their 2-session daily limit, the advisory lock serializes the evaluation and rejects the 3rd booking!

6. The Durable Background Worker & Transactional Outbox

The application runs an independent background daemon: src/worker.ts. It operates decoupled from Next.js web requests to guarantee that asynchronous jobs execute reliably even if web traffic spikes or server restarts occur.

6.1 The Transactional Outbox Pattern

When a court hold is created or a password reset is requested, the system does not immediately call an external email service or fire an untracked setTimeout. Doing so risks the dual-write failure problem (e.g. database commits, but email fails or Node process crashes).

Instead, the business service inserts a record into the Job table inside the exact same ACID database transaction!

6.2 Job Claiming via SKIP LOCKED

Look at src/modules/mail/worker.ts:

export async function processNextJob() {
  const jobs = await db.$queryRaw<Job[]>`
    UPDATE "Job" SET status='RUNNING', "lockedAt"=NOW(), attempts=attempts+1
    WHERE id = (
      SELECT id FROM "Job" 
      WHERE (status='PENDING' AND "runAt"<=NOW()) 
         OR (status='RUNNING' AND "lockedAt"<NOW()-INTERVAL '5 minutes')
      ORDER BY "runAt" 
      FOR UPDATE SKIP LOCKED 
      LIMIT 1
    )
    RETURNING *`;
  ...
}
Why This Is Industry-Standard Architecture
  1. FOR UPDATE SKIP LOCKED: If you run 5 worker processes across a cluster, each worker grabs a pending job and instantly locks it. Other workers skip the locked row and grab the next job without blocking! No worker ever processes the same job twice.
  2. Zombie Job Recovery: If a worker process crashes mid-job, the row remains in RUNNING status. The clause "lockedAt" < NOW() - INTERVAL '5 minutes' allows another worker to reclaim and complete the orphaned job!
  3. Scheduled Reminders: The worker automatically synchronizes 7-day, 1-day, and 0-day membership expiration reminders every 60 seconds without burdening web requests.

7. Top 15 Killer Viva Questions & High-Score Answers

Memorize these responses. These are the exact high-difficulty questions examiners love to ask to distinguish top-tier engineers.

Q1: Why did you store money in integer paise instead of float or Decimal?

Answer: "In IEEE-754 floating-point arithmetic used by JavaScript, binary fractions cannot represent decimal fractions like 0.1 or 0.2 accurately. For instance, 0.1 + 0.2 === 0.30000000000000004. In financial software, accumulating fractional rounding errors over thousands of ledger entries causes balance sheet discrepancies and auditing failures. By storing money as integer paise (1 INR = 100 paise), every addition, discount, and credit is exact to the integer."

Q2: What is the purpose of the Idempotency-Key header on mutations?

Answer: "If a customer clicks 'Pay' and their network drops before receiving the response, their mobile app or browser will automatically retry. Without idempotency, the server would charge their card or create an invoice twice. With our idempotency guard, the server hashes the actor ID, idempotency key, and request payload into the Checkout table. If an identical request arrives, the server returns the cached result with replayed: true without repeating the financial charge."

Q3: What happens if two members click the same court slot at the exact same millisecond?

Answer: "We defend against this at two layers. First, at the application layer, we acquire an exclusive row lock on the court via courtLock(). Second and most importantly, at the database engine level, we enforce a PostgreSQL GiST exclusion constraint (EXCLUDE USING gist) using the btree_gist extension. The database evaluates time interval overlaps in [startsAt, endsAt) for that court ID and rejects the colliding transaction with SQL error code 23P01. Exactly one succeeds; the second receives an explicit slot-taken error."

Q4: Why do you store plan benefits as a JSON snapshot in the Membership table instead of just referencing planId?

Answer: "Membership plans evolve over time—the club owner might increase the price of the Gold Plan from ₹5,000 to ₹6,000 or lower court discounts from 20% to 15%. If we only referenced planId, an active member who paid ₹5,000 under the old contract would suddenly lose their promised benefits or have inaccurate historical invoices. By storing an immutable planSnapshot JSON object on the Membership row, the customer's agreed benefits remain frozen for their entire term."

Q5: Explain the difference between Invoice, Payment, and PaymentAllocation. Why three models?

Answer: "This follows standard double-entry accounting. An Invoice represents a debt or obligation to pay (billed revenue). A Payment represents real money received from a customer (cash, card, UPI, gateway). A PaymentAllocation represents the mapping between payment and debt. This separation enables real-world scenarios like partial payments (paying ₹1,000 toward a ₹3,000 bill), bulk payments (one payment settling three court bookings), and credit notes without corrupting past transaction history."

Q6: How does the Cash Shift Float Reconciliation prevent cashier theft?

Answer: "A cashier cannot accept cash without opening a shift and declaring their opening drawer float. Throughout the shift, every cash payment, cash refund, and cash payout automatically links to that cashier's active cashShiftId under a row lock. At closing, the cashier inputs physical counted cash. The system compares counted cash against calculated cash (Opening + Receipts - Refunds - Payouts). If there is any discrepancy, the system refuses to close the shift until the cashier provides an audited written reason."

Q7: How does your background worker avoid race conditions when multiple worker processes are running?

Answer: "We use the PostgreSQL query clause FOR UPDATE SKIP LOCKED LIMIT 1. When Worker A queries for a pending job, PostgreSQL locks that specific row and returns it. If Worker B queries concurrently, PostgreSQL skips the locked row and returns the next pending job. This provides lock-free, zero-conflict horizontal scalability across multiple background workers."

Q8: Why did you choose a Modular Monolith instead of Microservices?

Answer: "In an athletic sports club, consistency is paramount—a court booking must atomically create an invoice, reserve inventory, check member quotas, and enqueue notification jobs. In a microservices architecture, this requires complex distributed two-phase commits (2PC) or Sagas prone to network failure and partial state inconsistency. A modular monolith allows us to maintain strict module boundaries while executing critical multi-domain workflows inside single, lightning-fast PostgreSQL ACID transactions."
